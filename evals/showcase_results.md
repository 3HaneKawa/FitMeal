## 1. 演示目标

这组材料不展示“测试了 270 条”这个数字，而是说明：

1. 为什么选这些风险切片。
2. 首轮真实 API 哪些能力可用，哪些不可用。
3. 每个失败属于实现、数据还是用例口径。
4. 修复顺序为什么不能按准确率从低到高排。
5. 下一轮如何验证，什么情况下不能声称通过。

## 5. 从失败得到的判断

### P0：先处理不可接受错误

安全请求必须停止普通推荐；过敏原不能进入推荐候选。风险类型也要与 PRD 一致，不能只检查“有没有拦截”。

过敏自动口径不能直接下结论。P032、P034 和 P259 的失败都由安全提示词触发。下一步需要人工复核候选食材、替换建议和风险提示，把“推荐了过敏原”“提醒避开过敏原”和“说明无匹配”分开判定。

### P0：信息不足时先追问

P047、P250 和 P249 暴露的是同一类问题：系统在条件不足或目标冲突时，仍然选择补全用户情况。该行为会破坏用户对推荐依据的信任。修复顺序是先定义必须追问的条件，再调整模型节点和提示词。

### P1：食材准确率要按原因拆分

52.5% 不能直接归因于模型。需要分别统计别名未命中、单位无法换算、复合食材、否定表达和候选库缺失。不同原因对应不同修复方式：补别名、改数据、改归一化或调模型。

### P2：延迟排在安全和澄清之后

P95 26.08 秒确实影响体验，首轮链路包含串行模型节点和同步数据检索。但当前最可能造成严重错误的是安全、过敏和缺失信息，不应为了降低延迟牺牲这些检查。

## 6. 复跑和验收标准

1. 不删除高风险用例，不修改期望值来提高通过率。
2. 每个修复关联失败类别和用例编号。
3. 先跑 P0 高风险切片，再跑 holdout。
4. 安全、过敏和解释类指标增加人工复核记录。
5. 复跑后保留首轮结果，分别报告修复前和修复后。
6. 只有真实 API 复跑达到门槛，才能写“优化后达标”。

## 7. 面试讲解口径

可以这样说明：

“首轮 270 条里，意图识别 95.4%，JSON 解析 100%，说明理解层和输出格式基本可用。但安全判定 88.9%、食材抽取 52.5%，过敏自动指标只有 14.3%。我没有直接把过敏低准确率解释成模型推荐了过敏原，因为人工查看后发现，P032、P034、P259 的失败是安全提示中的词被字符串规则误伤。下一步先统一判定口径，再修安全分类、追问和食材治理，最后复跑 holdout 和完整批次。当前这轮仍然是修复前基线。”

不能这样说明：

- 不能说系统已经达到上线标准。
- 不能用 270 条数量代替数据设计依据。
- 不能说过敏过滤真实准确率就是 14.3%。
- 不能把本地前端接口耗时写成 Dify API 延迟。
