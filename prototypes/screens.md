# FitMeal 页面结构与交互说明

> 更新时间：2026-10-09
> 对应前端：`web/`
> 运行地址：`http://127.0.0.1:8765/app/`
> 截图目录：`web/screenshots/`

## 1. 原型范围

当前原型是本地可运行 Demo，不是静态画板。左侧表单生成结构化请求，右侧展示 FastAPI 返回的结果。

实现边界：

- 本地前端调用 `POST /recommend`，展示推荐、外食、替换、营养和安全五类结果。
- Dify Chatflow 是另一条链路，从自然语言输入开始，经过参数抽取、安全判断、意图分类、FastAPI 和回答生成。两者分开测试，不把本地前端耗时写成 Dify API 耗时。
- F10 用户反馈尚未实现，原型没有“采纳”“不喜欢”按钮。

## 3. 页面结构

### 3.1 顶部状态栏

左侧为 FitMeal 标识。右侧显示本地服务状态和食谱数量，数据来自 `/health`。

### 3.2 左侧输入区

输入区包含：

1. 四个示例入口：自烹饪、外食、替换、安全拦截。
2. 一句话描述输入框。
3. 场景选择：自动判断、自己做饭、外食、替换、营养查询、安全测试。
4. 目标选择：减脂、增肌、维持。
5. 时间上限，默认 20 分钟。
6. 地域偏好：不限、川渝、粤式、江浙、北方。
7. 现有食材，用逗号分隔。
8. 过敏和忌口，仅填写明确说明。
9. 替换或营养查询时才显示的附加字段：原食材、查询食材、重量。

点击示例会回填输入，但用户仍可在提交前修改。

### 3.3 右侧结果区

结果区由标题、请求条件摘要和结果卡片组成。

请求条件摘要使用标签展示场景、目标、时间、地域和食材，便于确认系统实际收到了什么。

通用状态：

- 空状态：提示先设置条件。
- 加载状态：显示正在筛选候选和核算营养。
- 服务错误：显示无法连接推荐接口，并提示启动本地服务。
- 无匹配：说明当前数据没有候选，不生成伪结果。

## 4. 各场景输出

### 4.1 自烹饪

每张食谱卡片包含：

- 菜名、完成时间、份数、每份重量和地域。
- 匹配度。
- 热量、蛋白质、脂肪和碳水。
- 食材匹配状态：已有或需补充。
- 做法步骤。
- 热量来源及食材贡献比例。
- 注意事项。

评分按食材匹配 40%、营养目标 30%、时间 10%、地域 15%、多样性 5% 计算。营养区间是排序信号，只有用例明确写出营养断言时才作为硬性通过条件。

### 4.2 外食

外食结果不按品牌数据库给营养值，展示：

- 菜品或点餐方向。
- 适用范围和参考热量区间。
- 优先选择、控制分量的策略。
- 酱汁、主食、汤底等高风险的注意项。

### 4.3 食材替换

每个替换卡片展示：

- 原食材和目标替换食材。
- 适用目标或场景。
- 替换后的营养变化。
- 使用限制或需要留意的条件。

没有替换规则时显示数据缺口，不生成未经支持的建议。

### 4.4 营养查询

营养结果展示：

- 标准食材名。
- 每 100 克基础数据。
- 用户查询重量对应的热量、蛋白质、脂肪、碳水和纤维。
- 数据来源、置信等级和数据版本。

### 4.5 安全拦截

安全请求停止普通推荐，展示：

- 风险类型，例如 `extreme_low_calorie`。
- 为什么不能直接给方案。
- 建议咨询医生或注册营养师。

过敏请求与安全拦截分开处理。过敏场景应过滤候选后继续推荐；只有过滤后没有安全结果时，才进入无匹配状态。

## 5. 交互流程

```text
选择示例或填写表单
  -> 生成结构化 payload
  -> POST /recommend
  -> 显示加载状态
  -> FastAPI 调用规则、数据和评分逻辑
  -> 按 answer_type 渲染对应结果
  -> 用户查看条件摘要、推荐理由和风险提示
```

当前没有登录、历史记录、收藏和反馈提交。刷新页面会回到空状态。

## 6. 原型阶段的产品判断

1. 把条件放在同一屏，避免用户在多步表单中来回确认。
2. 结果先给决策，再给营养和做法，避免用户先读长文。
3. 每张卡片都显示“使用了什么、还缺什么”，比只说“健康”更容易判断是否可执行。
4. 外食只给可执行策略，不伪装成精确品牌营养数据。
5. 安全提示优先于推荐结果，不能在风险请求后继续展示普通食谱。
6. 本地前端和 Dify 链路分别保留，便于定位问题出在表单、服务还是模型节点。

## 7. 后续原型验证

1. 用 5 至 10 位目标用户测试三次推荐内能否做出选择。
2. 记录用户没有选择时，是因为候选项不合适、理由不足还是信息过多。
3. 验证是否需要增加“完全使用现有食材”和“允许补充一两样食材”两个入口。
4. 安全与澄清逻辑修复后，再设计 F10 反馈按钮和事件字段。
5. 对比列表和逐项卡片在手机端的阅读成本，再决定移动端结构。
