# FitMeal 页面结构与交互说明

> 更新时间：2026-10-10
> 对应前端：`web/`
> 运行地址：`http://127.0.0.1:8765/app/`
> 截图目录：`web/screenshots/`

## 1. 原型范围

当前原型是本地可运行的 Dify Chatflow Demo，不是静态画板。左侧只收集一句自然语言，右侧展示 Dify 返回的完整回答。

实现边界：

- 浏览器调用本地 FastAPI 的 `POST /chat`，不直接接触 Dify API Key。
- FastAPI 从项目根目录 `.env` 读取应用 Token，再调用 Dify Chatflow。
- Dify 内部经过参数抽取、安全判断、意图分类和数据服务请求；`POST /recommend` 只作为工作流内部的数据节点。
- Dify 不可用时直接显示错误，不回退到本地规则，也不把规则结果伪装成 Dify 结果。
- 回答底部提供“有帮助 / 没帮助”反馈；事件写入本地 CSV，但不会自动改变推荐排序。

## 3. 页面结构

### 3.1 顶部状态栏

左侧为 FitMeal 标识。右侧同时检查本地服务与 Dify 代理配置，显示“Dify 链路已配置”、食谱数量或未就绪状态。

### 3.2 左侧输入区

输入区只保留：

1. 五个示例入口：自烹饪、外食、替换、营养和安全拦截。
2. 一句话描述输入框。
3. “生成 Dify 建议”按钮。
4. 链路说明：浏览器只发送自然语言，API Key 留在服务端。

点击示例会填入对应问题并直接提交。页面不在浏览器里判断意图、提取食材或拼装结构化 payload。

### 3.3 右侧结果区

结果区由标题、真实链路耗时和回答卡片组成。

通用状态：

- 空状态：提示输入食材、目标或用餐场景。
- 加载状态：说明 Dify 正在理解需求、读取数据并生成建议，通常需要 20 至 40 秒。
- 服务错误：说明 Dify、8765 数据服务或 8766 向量服务未就绪。
- 成功状态：显示 `Dify Chatflow · 真实 API`、端到端耗时和 Dify 回答。

## 4. 输出内容

回答由 Dify 生成，可能包含推荐菜名、营养数字、食材匹配、制作步骤、外食策略、替换建议或安全说明。前端只负责安全地展示文本和基础 Markdown，不再按本地 `answer_type` 选择食谱、外食或营养卡片。

需要核对的输出口径：

- 营养计算和候选筛选来自 Python 数据服务，模型不能改写数值。
- 回答应说明数据来源、份量口径和必要的风险提示。
- 没有合适候选时应追问或说明限制，不能编造数据。
- 安全请求应优先给出拦截和就医建议，不继续普通推荐。

## 5. 交互流程

```text
选择示例或填写一句话
  -> POST /chat
  -> FastAPI 读取 .env 中的 Dify Token
  -> Dify Chatflow
  -> 参数抽取 / 安全判断 / 意图分类
  -> POST /recommend（Dify 内部数据节点）
  -> 知识库检索
  -> LLM 生成回答
  -> 前端安全渲染文本
  -> 用户点击“有帮助 / 没帮助”
  -> POST /feedback，仅记录事件
```

当前没有登录、历史列表、收藏、跨会话偏好记忆和反馈驱动排序。反馈事件文件不提交到公开仓库；`conversation_id` 保存在浏览器本地，用于延续 Dify 多轮对话。

## 6. 原型阶段的产品判断

1. 只保留一个自然语言入口，避免表单字段和模型抽取重复维护。
2. 页面明确标注真实 Dify 链路，不用本地规则结果制造“秒回”假象。
3. 等待时间较长时说明系统正在做什么，降低用户对无响应的误判。
4. 营养数字、匹配和风险提示继续由 Python 数据服务负责，模型只解释和表达。
5. 安全提示优先于推荐结果。
6. 反馈先验证“能不能采集、能不能复盘”，不急着把少量点击解释成个性化效果。
7. API Key 留在服务端，公开仓库只提供 `.env.example`。

## 7. 后续原型验证

1. 用 5 至 10 位目标用户测试三次推荐内能否做出选择。
2. 记录用户没有选择时，是因为候选项不合适、理由不足、等待过长还是信息过多。
3. 对比自由文本回答和结构化卡片的阅读成本，再判断是否需要 Dify 输出结构化结果。
4. 真实用户测试后，再评估对话反馈理解、偏好记忆和排序闭环。
5. 补充 Dify 单输入版首页、加载、推荐和安全拦截截图。
