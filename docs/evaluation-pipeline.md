# FitMeal 评测链路

> 更新时间：2026-10-10
> 适用范围：`evals/eval_set.csv`、代码层回归、Dify 真实 API 复跑和人工复核
> 结论口径：先看用例是否覆盖真实风险，再看失败能否归因；不把样本数量当成质量

## 1. 为什么做这套评测

FitMeal 不是普通菜谱搜索。一次回答同时涉及意图识别、参数抽取、过敏过滤、营养计算、候选排序和风险提示。只看几条“看起来不错”的案例，无法回答下面几个问题：

1. 用户没说清食材或目标时，系统会不会替用户编条件。
2. 用户明确说过敏原时，风险食材会不会进入推荐或替换。
3. 极端节食、医疗条件和不安全请求会不会被普通推荐覆盖。
4. 推荐的营养数字能不能回到数据表，而不是模型心算。
5. 修复一个问题后，之前已经通过的场景会不会回归。

因此评测集的设计目标不是追求“270 条”这个数字，而是把产品边界、风险后果和验收口径固定下来。

## 2. 用例从哪里来

用例不是从模型回答里随机复制，而是从 PRD 和能力矩阵反向拆解：

1. 先列出 v1 必须完成的能力，形成 `F1` 至 `F12`。
2. 再列出安全、边界、语言和数据风险，形成 `S`、`B`、`L` 等编号。
3. 每个编号写清楚输入、期望行为、禁止行为和失败阶段。
4. 按“用户真实会怎么表达”补充中文、口语、复合约束、中英混合和否定表达。
5. 对容易误判的安全用例，单独检查风险类型，不只看是否出现“已拦截”。

正式用例共 270 条，开发集 219 条，验收集 51 条。开发集用于定位和修改，验收集只用于验收，不参与调参，也不根据结果修改期望值。

风险分布为高风险 164 条、中风险 94 条、低风险 12 条。按主要行为分为：食谱推荐 80、外食建议 49、食材替换 48、安全拦截 45、澄清追问 21、用户反馈 12、不匹配处理 9、营养解释 6。

## 3. 一条用例包含什么

每条用例不是只写一句用户输入，而是保存完整判定信息：

| 字段 | 作用 |
| --- | --- |
| `case_id` / `split` | 固定用例编号和开发集 / 验收集归属 |
| `capability_id` / `prd_ref` | 说明它在验证哪项产品和需求 |
| `user_input` | 保留用户原话，测试真实表达 |
| `expected_*` | 记录期望意图、目标、食材、地域和时间 |
| `expected_behavior` | 应该推荐、追问、拦截还是记录反馈 |
| `pass_rule` | 机器或人工如何判定通过 |
| `forbidden_items` | 回答中不能出现的风险项或错误承诺 |
| `failure_stage` | 失败时优先归因到意图、抽取、安全、过滤、评分、解释、格式或数据 |
| `severity` / `data_sensitivity` | 决定失败后果和是否需要人工复核 |
| `data_version` | 让数据敏感结论可以复现 |

这种结构让失败可以落到具体阶段。例如“没识别出用户不能吃花生”不能笼统写成“模型效果差”，需要继续区分是参数抽取漏了过敏项、过滤规则没有执行，还是回答生成把安全提示写错。

## 4. 评测集怎样校验

运行代码层评测前，先检查用例本身是否自洽：

```powershell
uv run --python 3.12 python scripts/check_eval_set.py --strict
uv run --python 3.12 python scripts/check_eval_consistency.py
```

第一项检查字段、枚举、编号、开发集 / 验收集规模，以及能力矩阵引用是否合法。第二项检查评测规则与营养目标、数据表和评分口径是否一致。用例本身写错时，不允许先跑结果再解释。

## 5. 代码层评测怎么跑

代码层模式直接调用 `scripts/handler.handle()`，不调用大模型。它用于确认规则、数据和本地筛选逻辑是否稳定：

```powershell
uv run --python 3.12 python scripts/run_eval_set.py --cases evals/eval_set.csv
```

判定分三类：

1. `pass`：通过规则已经由机器断言验证。
2. `fail`：机器断言明确失败，需要归因和修复。
3. `blocked` / `not_ready`：该模式无法判断，或能力还没有接入完整链路，需要真实 API、LLM 或人工 rubric。

当前版本 `bv-a3e6abe13870` 的结果是 234 pass、10 fail、14 条待人工或 LLM 评分、12 条用户反馈对话用例未就绪。开发集为 190 / 8 / 11 / 10，验收集为 44 / 2 / 3 / 2。

代码层通过不等于产品可用。它只能说明“规则和数据没有明显回归”，不能代表 Dify 真实调用链已经正确。

## 6. 真实 API 评测怎么跑

真实 API 模式经过 Dify Chatflow、LLM、FastAPI 和回答生成节点，输出单独保存，不能和代码层结果混写。首轮修复前基线为：

| 指标 | 结果 | 目标 | 结论 |
| --- | ---: | ---: | --- |
| 意图识别 | 95.4% | ≥95% | 接近目标 |
| 目标抽取 | 91.3% | ≥90% | 达标 |
| 地域归一化 | 97.1% | ≥90% | 达标 |
| 时间抽取 | 97.9% | ≥90% | 达标 |
| JSON 解析 | 100% | 100% | 达标 |
| 安全判定 | 88.9% | ≥95% | 未达标 |
| 过敏自动口径 | 14.3% | 100% | 口径需人工复核 |
| 食材抽取 | 52.5% | ≥90% | 未达标 |
| P95 延迟 | 26.08 秒 | ≤8 秒 | 未达标 |

真实 API 批次共有 196 pass、58 fail、3 blocked、12 not_ready、1 error。公开仓库只保留汇总和脱敏案例，原始请求与回包留在本地。

## 7. 结果怎样判断

评测判断分三层，避免用一种分数解释所有问题：

1. **机器断言**：回答类型、推荐数量、营养区间、候选是否含过敏原、风险类型和 JSON 字段。
2. **人工 rubric**：解释是否忠实于结构化结果、冲突是否说明、降级方案是否可执行。
3. **高风险复核**：过敏、医疗、极端饮食和虚假营养数据必须人工看上下文，不能只用关键词命中。

例如过敏自动口径只有 14.3%，人工查看后发现 P032、P034、P259 中有回答是在说“不要用花生油”或“排除了蟹”，字符串规则把安全提示误判成泄露。这个发现说明先要修判定，再决定过滤逻辑是否需要修改。

## 8. 失败后怎样归因和修复

每条失败按下面顺序处理：

1. 看失败阶段，不先改提示词。
2. 区分实现问题、数据问题、用例 / PRD 问题。
3. 记录代表用例、根因、修复动作和同批复跑结果。
4. 安全、过敏和澄清问题优先于普通排序和性能。
5. 修复后先跑高风险切片和验收集，再跑完整 270 条。
6. 不删除高风险用例，不修改 holdout 期望，不把 blocked 或 not_ready 写成通过。

当前失败以缺少信息时追问、目标冲突、约束降级和个别候选数据覆盖为主。首轮真实 API 风险分类、过敏自动断言和食材抽取也已定位，但还需要真实 API 回归才能写“已修复”。

## 9. 最小用户反馈怎样进入链路

后端 `/feedback` 支持四类动作：采纳、不喜欢、太麻烦、换一批；当前单输入前端只在每个 Dify 回答下暴露“有帮助 / 没帮助”两个入口，尚未按单道食谱提供四个按钮。点击后调用 `POST /feedback`，记录 `request_id`、`recipe_id`、动作、原因和时间；当前页面把 Dify 回答的 `message_id` 作为关联编号，不细分到某一道推荐。

当前做到的是事件记录，不是自动学习偏好，也不会立刻改变下一次排序。事件文件 `runtime/feedback_events.csv` 只在本地保留，不提交公开仓库。后续只有在获得真实用户反馈后，才有依据判断按钮使用率、拒绝原因和排序调整是否有效。

## 10. 对外展示时怎么讲

可以讲：

- 270 条不是随机样本，而是按能力、风险和使用路径设计，开发集与验收集分离。
- 首轮结果既看通过率，也看失败阶段和人工复核，不把 `not_ready` 算成成功。
- 代码层和真实 API 分开说明，当前仍有安全和食材治理缺口。
- 反馈入口已经落地，但还需要真实用户数据才能验证是否会改善推荐。
- 营养计算器是独立于 Dify 的确定性工具，可以用固定食材、克重和份数复算；接口、页面和离线回归已通过，但这不等于真实用户验证或成品认可度。

不能讲：

- “270 条全部通过”或“系统已经上线可用”。
- “过敏真实准确率就是 14.3%”，因为这是未复核的自动口径。
- “用户反馈已经驱动个性化”，当前只记录事件，还没有闭环验证。
- “营养计算器已经通过真实用户验证”，当前完成的是接口、页面和离线回归，不是用户可用性测试。
