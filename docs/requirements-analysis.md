# FitMeal 需求分析

> 更新时间：2026-10-09
> 对应版本：v0.3.0
> 说明：本文记录需求判断和依据。当前尚未完成真实用户访谈，公开产品观察、场景拆解和自用验证只能作为待验证假设。

## 1. 要解决的问题

健身用户缺的通常不是菜谱，而是在具体条件下快速做出一顿饭的决定。

常见条件包括：

1. 冰箱里只剩几样食材，不想额外采购。
2. 正在减脂、增肌或维持，但不知道自己这一餐应该吃多少。
3. 只剩十几分钟，且厨具或调味有限制。
4. 当晚要外食，无法获得可靠菜品营养数据，但需要点餐策略。
5. 对某种食材过敏，普通推荐不能把风险项混进结果。

通用菜谱产品通常按菜名和食材搜索，回答“有什么菜”；FitMeal 要回答的是“以我现在的条件，这一顿选什么，为什么”。这要求产品同时处理信息收集、候选筛选、营养计算、风险拦截和解释。

## 2. 用户和场景假设

### 2.1 首要用户

有明确健身目标、每周训练 2 至 5 次、会自己做饭，但没有固定饮食计划的人。

细分场景：

| 用户 | 当下任务 | 主要顾虑 |
| --- | --- | --- |
| 减脂用户 | 控制总热量和脂肪，同时保证蛋白质 | 推荐清淡但没有饱腹感；营养数字没有依据 |
| 增肌用户 | 训练后补足蛋白质和适量碳水 | 被推荐高热量但蛋白质不足的餐食 |
| 维持用户 | 不想每天计算，但希望饮食不过度限制 | 选择过多，难以快速决定 |
| 高频外食用户 | 在餐厅或应酬中做相对合适的选择 | 品牌菜品营养数据不可靠；建议无法执行 |
| 明确过敏用户 | 排除风险食材并找到替代 | 推荐或替换建议遗漏过敏原 |

### 2.2 一个完整任务

以“家里有鸡胸肉、西兰花和鸡蛋，减脂，20 分钟内完成”为例：

1. 用户说出食材、目标和时间。
2. 系统识别意图并抽取条件。
3. 系统先判断是否存在医疗、极端饮食或过敏风险。
4. 系统从食谱库筛选候选，排除过敏原。
5. 系统按食材匹配、目标、时间和地域评分。
6. 系统现算每份重量、营养和食材级贡献。
7. 用户看到推荐理由、缺失食材、做法和风险提示。
8. 如果没有合适候选，系统说明限制并追问或建议放宽条件。

目前最重要的断点在第 3、4、8 步。首轮 API 评测已经发现：信息缺失时会直接推荐，过敏自动断言会误伤安全提示，冲突约束缺少降级说明。

## 3. 需求优先级

优先级按“出错后果”和“是否影响主任务”排序，而不是按开发工作量。

| 优先级 | 需求 | 判断依据 | v1 处理 |
| --- | --- | --- | --- |
| P0 | 安全拦截 | 极端节食、脱水、药物减肥和医疗请求可能造成健康风险 | 命中后停止普通推荐 |
| P0 | 过敏原过滤 | 推荐过敏食材属于不可接受错误 | 候选进入回答前过滤，保留人工复核 |
| P0 | 缺少信息时追问 | 替用户假设食材或目标会产生无依据回答 | 食材、目标缺失时先确认 |
| P1 | 食谱推荐 | 最高频主任务 | 输出 Top 3，优先使用现有食材 |
| P1 | 营养计算与来源 | 没有数值口径时无法判断推荐是否合理 | 由数据表和 Python 计算，不由模型心算 |
| P1 | 冲突约束处理 | 时间、工具、目标不能同时满足时，直接推荐会误导用户 | 明确说明冲突，给近似方案或放宽项 |
| P1 | 外食策略 | 外食用户无法依赖品牌营养数据 | 给选菜和点餐原则，不虚构品牌数值 |
| P2 | 食材替换 | 能降低采购成本，但依赖替换库覆盖 | 说明适用条件和营养变化 |
| P2 | 用户反馈 | 有助于后续个性化 | 已记录回答级最小反馈事件；对话理解、偏好持久化和排序闭环未实现，评测保留 not_ready |
| 非 v1 | 账号、支付、下单、医疗建议 | 增加合规和工程成本，不验证核心问题 | 不进入当前范围 |

## 4. 产品取舍

### 4.1 大模型负责什么

大模型适合处理自然语言理解、条件抽取和回答组织，不适合在没有数据表的情况下计算营养或决定候选是否安全。

当前分工：

- 模型：意图识别、参数抽取、冲突解释、回答表达。
- Python：候选筛选、评分、过敏过滤、份量与营养计算、风险短路。
- 数据表：食谱、营养、外食、目标规则、替换规则、别名和单位。

这一分工的代价是链路更长、节点更多，首轮真实 API P95 达到 26.08 秒。当前先保安全和可追溯，再处理延迟。

### 4.2 为什么不做“全能营养师”

医疗条件、孕期、疾病和未成年人的营养方案需要专业资质、完整病史和更高合规要求。v1 不提供个体化医疗建议，只在识别到风险时拒绝并建议咨询专业人士。

### 4.3 为什么先做 270 条评测集

样本数量本身不能说明产品可用。270 条用例的作用是固定范围、风险和验收口径：

- 219 条开发集用于定位问题。
- 51 条验收集只用于验收，不用于调参。
- 164 条高风险用例覆盖安全、过敏、极端约束和信息缺失。
- 每条用例记录期望行为、通过规则、失败阶段和数据版本。

首轮真实 API 结果中，意图识别 95.4%、JSON 解析 100%，但安全判定 88.9%、食材抽取 52.5%、过敏自动口径 14.3%。因此下一步不是继续加功能，而是先修安全、澄清和数据治理。

## 6. 验收标准

### 功能验收

1. 浏览器中的一句话请求经 `/chat` 代理进入 Dify，并能完成自烹饪、外食、替换、营养和安全五类请求。
2. 本地链路应能通过 `uv` 启动 FastAPI 和向量服务；Dify 不可用时明确报错，不静默降级为本地规则。
3. 推荐结果包含份数、每份重量、每份营养和食材级拆解。
4. 没有候选时明确说明缺口，不编造食谱和营养数值。

### 质量验收

1. 安全 LLM 判定准确率不低于 95%。
2. 意图识别不低于 95%，目标抽取、地域和时间抽取不低于 90%。
3. JSON 解析通过率保持 100%。
4. 过敏过滤在生产候选进入回答前达到 100%，机器断言需要人工复核。
5. P95 响应时间不高于 8 秒。该指标首轮未达标，排在安全和澄清之后处理。

### 研究验收

1. 招募 5 至 10 位目标用户完成可用性测试。
2. 记录用户能否在三次推荐内做出选择。
3. 记录不选择的原因，区分没有合适结果、推荐理由不足和信息太多。
4. 访谈或测试结论更新到 PRD，再调整需求优先级。

## 7. 当前未验证的判断

以下内容目前只有假设，不能写入求职成果：

1. 用户是否愿意长期使用 FitMeal。
2. 用户是否愿意为饮食决策付费。
3. Top 3 数量是否比 Top 1 或 Top 5 更合适。
4. 单输入方式是否足够承载复杂条件，以及是否需要在后续版本增加结构化辅助。
5. 降低 P95 后，用户是否仍会因为结果不信任而放弃。
6. 外食建议是否能促成实际点餐决策。

下一步需要先完成小范围用户任务测试，再决定是否调整 MVP 范围。
