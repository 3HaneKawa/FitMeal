# FitMeal 轻食令 PRD

> 版本：v0.4.0
> 更新时间：2026-10-10
> 当前状态：单输入前端、FastAPI `/chat` 代理、Dify Chatflow 和 270 条正式评测集均已可运行；真实 API 首轮结果作为修复前基线保留

## 1. 文档目的

本文定义 FitMeal v1 的目标用户、使用场景、功能范围、数据与安全要求、验收标准和当前缺口。文档记录的是已经实现或明确纳入 v1 验证的能力，不把尚未完成的能力写成上线结果。

## 2. 用户与问题

### 2.1 目标用户

首要用户是有明确健身目标、但没有稳定饮食计划的人，主要包括：

1. 减脂期用户：需要控制总热量和脂肪，同时保证蛋白质摄入。
2. 增肌期用户：关注蛋白质和训练后补充，但不能接受无依据的高热量建议。
3. 维持期用户：希望饮食不过度限制，也不想每天重复计算。
4. 外食频率较高的用户：知道要控制饮食，但到了餐厅不知道具体怎么点。

用户至少需要提供目标；如果要得到自烹饪推荐，还应提供现有食材、可接受的时间或地域偏好。缺少关键条件时，产品应先追问，而不是替用户假设。

### 2.2 典型场景

1. 用户说“家里有鸡胸肉、西兰花和鸡蛋，减脂，20 分钟内做完”，希望得到可以直接执行的晚餐。
2. 用户说“今晚和同事吃川菜，我在减脂”，希望得到点餐顺序和避开高油菜品的建议。
3. 用户说“没有米饭，主食可以换成什么”，希望看到替换关系、营养变化和适用条件。
4. 用户说“100 克鸡胸肉有多少蛋白质”，希望看到来源、份量和每份口径。
5. 用户提出断食、脱水、药物减肥或单一饮食方案时，产品需要拒绝提供危险执行步骤，并给出安全提醒。

### 2.3 用户研究状态

目前完成了用户问题假设和访谈问题库，尚未完成真实用户访谈。现有需求结论来自公开产品观察、健身饮食场景拆解和自用流程验证。作品集和面试讲解中不把这部分写成已完成的访谈研究。

## 3. v1 要解决什么

### 3.1 用户能得到什么结果

1. 在三次推荐内决定这一餐吃什么。
2. 推荐尽量使用用户已经有的食材，并明确列出缺少的食材。
3. 每个推荐都能看到份数、每份重量、热量、蛋白质、脂肪、碳水和食材级营养拆解。
4. 外食场景不编造品牌营养数据，优先给出可执行的选菜与点餐策略。
5. 过敏、极端饮食和医疗风险不能被普通推荐覆盖。

### 3.2 项目要验证的假设

1. 验证健身人群是否会为“这顿吃什么”的决策成本买单。
2. 用可追溯的数据和规则替代大模型自由计算。
3. 建立一套可以复跑的评测集，先发现高风险问题，再扩展普通功能。

### 3.3 当前不做什么

v1 不包含账号体系、社交、支付、外卖下单、医疗级营养建议、疾病或孕期特殊人群方案，以及长期饮食习惯建模。知识库只用于后置背景说明，不作为营养事实来源，也不参与推荐排序。

## 4. 实现边界

1. 大模型只负责理解、解释和表达。
2. 营养计算、候选筛选、评分和过敏过滤由 Python 与数据表完成。
3. 每个推荐都要能说出使用了什么数据、满足或没有满足什么约束。
4. 安全分为两条路径：过敏走候选过滤，极端低热量、单一饮食、医疗条件和不安全建议走请求拦截。
5. 缺少关键信息时先追问；没有合适候选时说明原因，不伪造食谱或营养数值。

## 5. 一次请求怎么处理

```text
用户输入
  ↓
意图识别与参数抽取
  ↓
安全判断
  ├─ 命中 S2-S5：返回安全提醒，停止推荐
  └─ 未命中：进入对应功能分支
          ├─ cook：过敏过滤 → 候选筛选 → 评分排序 → 输出食谱
          ├─ eat_out：按目标、地域和点餐限制输出建议
          ├─ substitute：查询替换关系与营养变化
          ├─ nutrition_analysis：返回营养数值与来源
          └─ provenance：返回数据来源和数据版本
```

浏览器只提交一句自然语言，调用 FastAPI 的 `POST /chat`。服务端代理持有 Dify API Key，再调用 Dify Chatflow；Dify 内部按需通过 `POST /recommend` 读取 Python 数据服务。前端不在浏览器里拆规则、拼结构化 payload，也不在 Dify 不可用时回退到本地推荐。

```text
浏览器单输入前端
  → POST /chat（FastAPI 代理）
  → Dify Chatflow
  → POST /recommend（Dify 内部数据节点）
  → 回答生成
  → 返回浏览器
```

## 7. 数据与规则

### 7.1 数据资产

当前数据快照：

| 数据表 | 行数 | 用途 |
| --- | ---: | --- |
| `recipes.csv` | 208 | 食谱、食材、烹饪时间和目标标签 |
| `nutrition.csv` | 159 | 每 100 克食材营养值及来源 |
| `eat_out_foods.csv` | 50 | 外食菜品类型、地域和点餐策略 |
| `goal_rules.csv` | 3 | 减脂、增肌和维持的营养区间 |
| `substitutions.csv` | 30 | 食材替换关系与说明 |
| `ingredient_aliases.csv` | 24 | 食材别名归一化 |
| `unit_conversions.csv` | 19 | 克、毫升、勺、份等单位换算 |

营养库来源包括 USDA FoodData Central、中国食物成分表和本地补充值，数据字典中保留来源、置信等级和版本。食谱营养值由食材克重现算，不允许在食谱表里手填后直接展示。

### 7.2 推荐评分

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 食材匹配 | 40% | 是否尽量使用用户现有食材 |
| 营养目标 | 30% | 是否符合减脂、增肌或维持规则 |
| 时间限制 | 10% | 是否满足用户给出的烹饪时间 |
| 地域偏好 | 15% | 是否匹配用户地域或口味场景 |
| 多样性 | 5% | 是否避免连续推荐相同组合 |

口味偏好 v1 只采集，不参与评分。反馈事件只用于本地复盘，不自动写入偏好或排序。营养区间是评分信号；只有测试用例明确写出营养断言时，才作为该用例的硬性通过条件。

### 7.3 失败处理

1. 缺少食材、目标或关键约束：先追问。
2. 食材没有候选：说明数据覆盖不足，给出放宽条件或替换方案。
3. 目标冲突：说明不能同时完全满足的约束，要求用户选择主目标。
4. 时间和条件冲突：说明当前条件没有合格结果，不假装满足全部限制。
5. 安全请求：停止普通推荐，返回安全提醒。

## 8. 测试与通过条件

### 8.1 测试集构成

`evals/eval_set.csv` 共 270 条：

- 开发集 219 条，验收集 51 条。
- 高风险 164 条、中风险 94 条、低风险 12 条。
- 覆盖食谱推荐、外食、替换、营养、安全拦截、澄清追问、不匹配处理和用户反馈占位；最小事件记录与 12 条对话式反馈用例分开验收。
- 每条用例记录能力编号、PRD 引用、期望行为、风险类型、通过规则、失败阶段、严重度和数据版本。

验收集只用于验收，不用于调参。修复时不能通过删除高风险用例或放宽期望值来人为提高通过率。

### 8.2 通过标准

| 指标 | 标准 | 首轮真实 API 结果 |
| --- | ---: | ---: |
| 意图识别准确率 | ≥95% | 95.4%，247/259 |
| 目标抽取准确率 | ≥90% | 91.3%，179/196 |
| 地域归一化准确率 | ≥90% | 97.1%，100/103 |
| 时间抽取准确率 | ≥90% | 97.9%，47/48 |
| JSON 解析通过率 | 100% | 100%，270/270 |
| 安全 LLM 判定准确率 | ≥95% | 88.9%，40/45 |
| 过敏过滤准确率 | 100% | 自动口径 14.3%，2/14，需人工复核 |
| 食材抽取准确率 | ≥90% | 52.5%，73/139 |
| P95 响应时间 | ≤8 秒 | 26.08 秒 |
| 平均单次成本 | 参考项 | $0.0017/次 |

首轮 API 总体结果为 196 pass / 58 fail / 3 blocked / 12 not_ready / 1 error。失败按来源分为实现问题 39 条、数据问题 20 条、PRD 或用例问题 15 条，按优先级分为 P0 14 条、P1 45 条、P2 15 条。

### 8.3 不进入下一轮的条件

出现以下情况时，不进入下一轮功能扩展：

1. 过敏原被推荐，或安全提示无法被用户识别。
2. 极端低热量、脱水、药物减肥等请求继续输出危险步骤。
3. 营养数值无法追溯到数据表。
4. JSON 解析失败率超过 5%。
5. P95 延迟持续超过 15 秒，且影响主要流程。

## 9. 当前缺口与修改顺序

### P0

1. 安全风险分类不稳定，P037、P213、P215 等用例的 `risk_type` 需要和 PRD 判据重新对齐。
2. 过敏自动断言把“不要用花生油”“都不含鸡蛋”“注意蟹粉”等安全提示判成禁用项，需要增加人工复核和上下文判定。
3. 缺少食材信息时仍会直接推荐，需要在推荐前增加强制澄清规则。

### P1

1. 食材抽取准确率只有 52.5%，需要把别名、单位、复合食材、否定表达和候选缺失分开归因。
2. 外食和替换分支存在来源、营养变化和品牌数据边界问题，需要补断言与人工 rubric。
3. 时间、工具和营养约束互相冲突时，缺少可解释的降级路径。

### P2

1. 合并可以并行的模型节点，减少重复模型调用和同步检索，降低 P95 延迟。
2. 在真实用户测试后，再评估把采纳和拒绝事件用于偏好持久化、候选排除与排序闭环。
3. 本轮不安排真实用户访谈；若后续要验证三次推荐内的决策率和采纳情况，再单独招募 5 至 10 位目标用户。
