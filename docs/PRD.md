# FitMeal 轻食令 PRD

> 版本：v0.6.0
> 更新时间：2026-10-10
> 当前状态：单输入前端、FastAPI `/chat` 代理、Dify Chatflow、独立营养计算器和 270 条正式评测集均已可运行；真实 API 首轮结果作为修复前基线保留；新增供墨刀 AI 使用的低保真原型生成规格

## 1. 文档目的

本文定义 FitMeal v1 的目标用户、使用场景、功能范围、数据与安全要求、验收标准和当前缺口。文档记录的是已经实现或明确纳入 v1 验证的能力，不把尚未完成的能力写成上线结果。

### 1.1 墨刀 AI 使用说明

本文同时承担两份用途：

1. 第 2 至第 9 节描述真实产品需求、实现边界、数据规则和验收口径。
2. 第 10 节是专门给墨刀 AI 的低保真原型生成规格；生成原型时优先读取第 10 节，并把第 2、3、6、7 节作为文案和功能上下文。

墨刀 AI 只用于生成低保真结构和交互状态，不负责证明功能已经上线，也不把首轮评测指标、接口地址、API Key、Dify 节点等实现细节画进用户界面。可直接复制使用的短提示词见 `docs/modao-prototype-prompt.md`。

## 2. 用户与问题

### 2.1 目标用户

首要用户是有明确健身目标、但没有稳定饮食计划的人，主要包括：

1. 减脂期用户：需要控制总热量和脂肪，同时保证蛋白质摄入。
2. 增肌期用户：关注蛋白质和训练后补充，但不能接受无依据的高热量建议。
3. 维持期用户：希望饮食不过度限制，也不想每天重复计算。
4. 外食频率较高的用户：知道要控制饮食，但到了餐厅不知道具体怎么点。

用户至少需要提供目标；如果要得到自烹饪推荐，还应提供现有食材、可接受的时间或地域偏好。缺少关键条件时，产品应先追问，而不是替用户假设。

### 2.2 典型场景

1. 用户说“家里有鸡胸肉、西兰花和鸡蛋，减脂，20 分钟内做完”，希望得到可以直接执行的晚餐。
2. 用户说“今晚和同事吃川菜，我在减脂”，希望得到点餐顺序和避开高油菜品的建议。
3. 用户说“没有米饭，主食可以换成什么”，希望看到替换关系、营养变化和适用条件。
4. 用户说“100 克鸡胸肉有多少蛋白质”，希望看到来源、份量和每份口径。
5. 用户提出断食、脱水、药物减肥或单一饮食方案时，产品需要拒绝提供危险执行步骤，并给出安全提醒。
6. 用户已经知道一餐用了哪些食材和克重，希望不经过自然语言推荐，直接得到整份与每份营养结果。

### 2.3 用户研究状态

目前完成了用户问题假设和访谈问题库，尚未完成真实用户访谈。现有需求结论来自公开产品观察、健身饮食场景拆解和自用流程验证。作品集和面试讲解中不把这部分写成已完成的访谈研究。

## 3. v1 要解决什么

### 3.1 用户能得到什么结果

1. 在三次推荐内决定这一餐吃什么。
2. 推荐尽量使用用户已经有的食材，并明确列出缺少的食材。
3. 每个推荐都能看到份数、每份重量、热量、蛋白质、脂肪、碳水和食材级营养拆解。
4. 外食场景不编造品牌营养数据，优先给出可执行的选菜与点餐策略。
5. 过敏、极端饮食和医疗风险不能被普通推荐覆盖。
6. 已知食材和克重时，可以通过独立计算器得到可追溯的热量与营养结果；未识别食材必须明确提示。

### 3.2 项目要验证的假设

1. 验证健身人群是否会为“这顿吃什么”的决策成本买单。
2. 用可追溯的数据和规则替代大模型自由计算。
3. 建立一套可以复跑的评测集，先发现高风险问题，再扩展普通功能。

### 3.3 当前不做什么

v1 不包含账号体系、社交、支付、外卖下单、医疗级营养建议、疾病或孕期特殊人群方案，以及长期饮食习惯建模。知识库只用于后置背景说明，不作为营养事实来源，也不参与推荐排序。

## 4. 实现边界

1. 大模型只负责理解、解释和表达。
2. 营养计算、候选筛选、评分和过敏过滤由 Python 与数据表完成。
3. 每个推荐都要能说出使用了什么数据、满足或没有满足什么约束。
4. 安全分为两条路径：过敏走候选过滤，极端低热量、单一饮食、医疗条件和不安全建议走请求拦截。
5. 缺少关键信息时先追问；没有合适候选时说明原因，不伪造食谱或营养数值。

## 5. 一次请求怎么处理

```text
用户输入
  ↓
意图识别与参数抽取
  ↓
安全判断
  ├─ 命中 S2-S5：返回安全提醒，停止推荐
  └─ 未命中：进入对应功能分支
          ├─ cook：过敏过滤 → 候选筛选 → 评分排序 → 输出食谱
          ├─ eat_out：按目标、地域和点餐限制输出建议
          ├─ substitute：查询替换关系与营养变化
          ├─ nutrition_analysis：返回营养数值与来源
          └─ provenance：返回数据来源和数据版本
```

浏览器只提交一句自然语言，调用 FastAPI 的 `POST /chat`。服务端代理持有 Dify API Key，再调用 Dify Chatflow；Dify 内部按需通过 `POST /recommend` 读取 Python 数据服务。前端不在浏览器里拆规则、拼结构化 payload，也不在 Dify 不可用时回退到本地推荐。

```text
浏览器单输入前端
  → POST /chat（FastAPI 代理）
  → Dify Chatflow
  → POST /recommend（Dify 内部数据节点）
  → 回答生成
  → 返回浏览器
```

独立营养计算器不进入这条链路。它接收结构化的食材和克重，只做确定性换算：

```text
营养计算页
  → POST /nutrition/calculate
  → data_entry.calculate_nutrition()
  → nutrition.csv + ingredient_aliases.csv + unit_conversions.csv
  → 整份 / 每份营养、食材拆解、来源和未识别项
```

### 6.1 独立营养计算器（归入 F4 / F12）

入口为 `http://127.0.0.1:8765/app/nutrition.html`，调用 `POST /nutrition/calculate`。它不是新的产品能力编号，而是 F4 营养估算和 F12 份数基准面向“已知食材与克重”场景的独立用户入口。

输入：

1. 一组食材名称和克重，至少一条。
2. 份数，范围 1 至 100，默认 1。
3. 食材可以使用营养库标准名，也可以使用已登记的别名。

输出：

1. 全部输入食材的整份总营养和总重量。
2. 按份数换算后的每份营养和每份重量。
3. 食材级热量、蛋白质、脂肪、碳水和膳食纤维拆解，以及各食材的热量占比。
4. 每个已识别食材的数据来源和可信度字段。
5. `unresolved` 未识别项及原因。

规则与边界：

1. 只使用 `data/nutrition.csv` 每 100 克数据和已登记别名，不允许大模型改写数值。
2. 不调用 LLM、不经过 Dify、不写入数据表；请求结果不会改变推荐排序。
3. 份数只影响每份结果，不改变用户输入的食材总重量。
4. 未识别食材不按 0 静默处理，也不计入合计；页面必须提示先补营养或别名数据。
5. 结果只说明此次输入的估算值，不代表完整饮食方案，也不替代医疗或个体化营养建议。

## 7. 数据与规则

### 7.1 数据资产

当前数据快照：

| 数据表 | 行数 | 用途 |
| --- | ---: | --- |
| `recipes.csv` | 208 | 食谱、食材、烹饪时间和目标标签 |
| `nutrition.csv` | 159 | 每 100 克食材营养值及来源 |
| `eat_out_foods.csv` | 50 | 外食菜品类型、地域和点餐策略 |
| `goal_rules.csv` | 3 | 减脂、增肌和维持的营养区间 |
| `substitutions.csv` | 30 | 食材替换关系与说明 |
| `ingredient_aliases.csv` | 24 | 食材别名归一化 |
| `unit_conversions.csv` | 19 | 克、毫升、勺、份等单位换算 |
| `target_ingredients.csv` | 48 | 食材覆盖施工单，用于追踪目标道数与现状；不参与推荐排序和营养计算 |

营养库来源包括 USDA FoodData Central、中国食物成分表和本地补充值，数据字典中保留来源、置信等级和版本。食谱营养值由食材克重现算，不允许在食谱表里手填后直接展示。`target_ingredients.csv` 是内部施工单，不是营养事实来源。

### 7.2 推荐评分

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 食材匹配 | 40% | 是否尽量使用用户现有食材 |
| 营养目标 | 30% | 是否符合减脂、增肌或维持规则 |
| 时间限制 | 10% | 是否满足用户给出的烹饪时间 |
| 地域偏好 | 15% | 是否匹配用户地域或口味场景 |
| 多样性 | 5% | 是否避免连续推荐相同组合 |

口味偏好 v1 只采集，不参与评分。反馈事件只用于本地复盘，不自动写入偏好或排序。营养区间是评分信号；只有测试用例明确写出营养断言时，才作为该用例的硬性通过条件。

### 7.3 失败处理

1. 缺少食材、目标或关键约束：先追问。
2. 食材没有候选：说明数据覆盖不足，给出放宽条件或替换方案。
3. 目标冲突：说明不能同时完全满足的约束，要求用户选择主目标。
4. 时间和条件冲突：说明当前条件没有合格结果，不假装满足全部限制。
5. 安全请求：停止普通推荐，返回安全提醒。
6. 营养计算器遇到未识别食材：继续计算已识别项，同时明确列出未识别项和原因；全部未识别时返回 0 结果和补数据提示，不伪造估算值。

## 8. 测试与通过条件

### 8.1 测试集构成

`evals/eval_set.csv` 共 270 条：

- 开发集 219 条，验收集 51 条。
- 高风险 164 条、中风险 94 条、低风险 12 条。
- 覆盖食谱推荐、外食、替换、营养、安全拦截、澄清追问、不匹配处理和用户反馈占位；最小事件记录与 12 条对话式反馈用例分开验收。
- 每条用例记录能力编号、PRD 引用、期望行为、风险类型、通过规则、失败阶段、严重度和数据版本。

验收集只用于验收，不用于调参。修复时不能通过删除高风险用例或放宽期望值来人为提高通过率。

### 8.3 不进入下一轮的条件

出现以下情况时，不进入下一轮功能扩展：

1. 过敏原被推荐，或安全提示无法被用户识别。
2. 极端低热量、脱水、药物减肥等请求继续输出危险步骤。
3. 营养数值无法追溯到数据表。
4. JSON 解析失败率超过 5%。
5. P95 延迟持续超过 15 秒，且影响主要流程。

## 9. 当前缺口与修改顺序

### P0

1. 安全风险分类不稳定，P037、P213、P215 等用例的 `risk_type` 需要和 PRD 判据重新对齐。
2. 过敏自动断言把“不要用花生油”“都不含鸡蛋”“注意蟹粉”等安全提示判成禁用项，需要增加人工复核和上下文判定。
3. 缺少食材信息时仍会直接推荐，需要在推荐前增加强制澄清规则。

### P1

1. 食材抽取准确率只有 52.5%，需要把别名、单位、复合食材、否定表达和候选缺失分开归因。
2. 外食和替换分支存在来源、营养变化和品牌数据边界问题，需要补断言与人工 rubric。
3. 时间、工具和营养约束互相冲突时，缺少可解释的降级路径。

### P2

1. 合并可以并行的模型节点，减少重复模型调用和同步检索，降低 P95 延迟。
2. 在真实用户测试后，再评估把采纳和拒绝事件用于偏好持久化、候选排除与排序闭环。
3. 本轮不安排真实用户访谈；若后续要验证三次推荐内的决策率和采纳情况，再单独招募 5 至 10 位目标用户。

## 10. 低保真原型生成规格（供墨刀 AI）

> 用途：为墨刀 AI 提供可直接生成 Web 端低保真交互原型的结构性说明。该规格只描述页面、信息、状态和交互，不代表高保真视觉稿，也不代表真实用户验证结果。

### 10.1 生成目标

生成一套桌面端 FitMeal 轻食令低保真原型，帮助面试官在 2 至 3 分钟内看懂完整产品闭环：

1. 用户用一句话说出饮食需求。
2. 系统先生成建议，信息不足时追问，命中安全风险时停止普通推荐。
3. 推荐结果说明使用食材、缺失食材、份量、营养和推荐理由。
4. 已知食材和克重时，用户可以使用独立营养计算器得到可追溯结果。
5. 用户可以记录“有帮助 / 没帮助”，但原型不表现个性化排序闭环。

生成时不要绘制技术架构、Dify 节点、接口地址、API Key、测试通过率、数据表字段或后台代码。技术链路只在 PRD 和面试讲解中出现，不进入用户界面。

### 10.2 画布与整体结构

| 项目 | 规格 |
| --- | --- |
| 终端 | Web / 桌面端 |
| 画板 | 1440 × 1024 |
| 页面结构 | 顶部导航 + 左侧需求输入 + 右侧结果反馈 |
| 导航项 | FitMeal 轻食令、推荐首页、营养计算、数据工具 |
| 首页输入区宽度 | 约 36% |
| 首页结果区宽度 | 约 64% |
| 营养计算页 | 顶部导航 + 左侧食材录入 + 右侧计算结果 |
| 页面关系 | 首页与营养计算页平级；数据工具作为次要入口放在导航末尾 |

所有页面沿用同一顶部导航、颜色、圆角、按钮和状态提示，不要为每个画板重新发明一套组件。

### 10.3 画板清单

| 编号 | 画板名称 | 主要内容 | 必须体现的状态 |
| --- | --- | --- | --- |
| P01 | 首页-空状态 | 一句话输入框、五个示例入口、结果区空状态 | 用户还不知道系统能做什么 |
| P02 | 首页-生成中 | 输入内容回显、提交按钮禁用、加载文案 | 完整生成通常需要 20 至 40 秒 |
| P03 | 建议结果-成功 | 推荐菜名、理由、食材、缺失项、份量、营养、反馈 | 信息完整且可执行 |
| P04 | 建议结果-追问 | 缺少必要条件时，只提出一个明确问题 | 不直接编造推荐 |
| P05 | 建议结果-安全拦截 | 风险说明、停止普通推荐、就医或求助提示 | 安全优先于推荐 |
| P06 | 营养计算-空状态 | 食材行、克重、份数、计算按钮 | 明确只接收克重 |
| P07 | 营养计算-成功 | 整份和每份营养、食材明细、来源、热量占比 | 数值和口径可追溯 |
| P08 | 营养计算-部分未识别 | 已识别食材继续计算，未识别食材单独提示 | 不静默按 0 处理 |
| P09 | 反馈已记录 | 有帮助 / 没帮助按钮和提交结果 | 反馈不改变本次推荐 |
| P10 | 数据总览（可选） | 食谱、营养、别名等数据量概览 | 作为数据闭环补充证据 |
| P11 | 数据录入（可选） | 新增食材或食谱的字段与校验 | 只在面试需要时展示 |

如果墨刀 AI 单次生成数量受限，先生成 P01 至 P07，再使用补全提示词生成 P08 至 P11。不要为了凑页面而重复生成相同布局。

### 10.4 首页与建议结果规格

#### P01 首页-空状态

顶部导航右侧显示“服务已连接”或“正在连接”的状态标签，不展示供应商名称。

左侧输入区包含：

1. 标题：把这一餐说清楚。
2. 说明：用一句话说明现有食材、目标、时间和忌口。
3. 五个示例入口：自烹饪、外食、替换、营养、安全拦截。
4. 多行输入框，占位文案为“例：我有鸡胸肉、西兰花和鸡蛋，减脂，想 20 分钟内做完”。
5. 主按钮：生成建议。
6. 辅助说明：页面只提交自然语言，不在浏览器里判断和拼装规则。

右侧结果区为空状态，标题为“等待输入”，正文说明可以输入需求或点击示例，结果会展示建议、份量和数据来源。

#### P02 首页-生成中

保留 P01 的页面结构。提交按钮显示“正在生成”并禁用。结果区显示三点加载动画和以下文案：

1. 正在理解需求。
2. 正在匹配食材和营养数据。
3. 正在生成可执行建议。

加载状态不能使用“已经完成”或伪造的进度百分比。

#### P03 建议结果-成功

结果区标题为“晚餐建议已生成”，并显示用户原始需求的简短回显。至少展示三条候选：

1. 黑椒鸡胸炒西兰花。
2. 番茄鸡蛋配糙米。
3. 香煎鸡胸蔬菜碗。

第一条卡片展开，展示：

1. 推荐理由：优先使用现有食材，20 分钟内完成，符合减脂目标。
2. 现有食材：鸡胸肉、西兰花、鸡蛋。
3. 需要补充：黑胡椒、少量橄榄油。
4. 份量：2 份。
5. 每份重量：175 克。
6. 每份营养：124 kcal、蛋白质 19.7 克、脂肪 2.4 克、碳水 6.6 克、膳食纤维 2.6 克。
7. 数据来源：本地营养表。
8. 底部反馈：这个建议有帮助吗？有帮助 / 没帮助。

第二条和第三条只展示菜名、理由摘要、时间和热量区间，避免首屏信息过载。所有数字只作为原型展示样例，不在页面上写“真实用户结果”。

#### P04 建议结果-追问

当输入只有“今晚吃什么”时，结果区不直接推荐，显示一个问题：

> 为了给你更合适的建议，先确认一下：你更想减脂、增肌还是维持体重？

下方提供三个快捷选项和“补充其他要求”。追问只问一个最关键的问题，不同时抛出多个表单字段。

#### P05 建议结果-安全拦截

当输入涉及极端断食、脱水、药物减肥或医疗风险时，结果区使用警示样式展示：

1. 标题：这个需求不适合继续生成饮食方案。
2. 说明：极端节食或自行用药可能带来健康风险。
3. 说明：系统不会提供危险执行步骤，也不会用普通推荐覆盖风险。
4. 建议：咨询医生或注册营养师。
5. 提供“返回修改需求”按钮，不提供继续推荐按钮。

### 10.5 营养计算页规格

#### P06 营养计算-空状态

页面左侧为录入区，右侧为结果区。顶部导航中的“营养计算”处于当前状态。

左侧包含：

1. 标题：把食材和克重算清楚。
2. 说明：输入这一餐的实际用量，系统按本地营养表计算。
3. 食材输入行：鸡胸肉、150 克。
4. 食材输入行：西兰花、200 克。
5. “+ 添加食材”按钮。
6. 份数输入：2 份。
7. 主按钮：计算营养。
8. 口径说明：营养值来自本地营养表，当前只接收克重。

右侧显示空状态标题“等待录入”，说明计算后会展示整份、每份、食材明细和数据来源。

#### P07 营养计算-成功

结果区显示：

1. 整份总计：350 克、248 kcal。
2. 每份结果：175 克、124 kcal。
3. 整份营养：蛋白质 39.4 克、脂肪 4.7 克、碳水 13.2 克、膳食纤维 5.2 克。
4. 每份营养：蛋白质 19.7 克、脂肪 2.4 克、碳水 6.6 克、膳食纤维 2.6 克。
5. 食材明细表：鸡胸肉 150 克，热量 180 kcal；西兰花 200 克，热量 68 kcal。
6. 热量占比：鸡胸肉约 73%，西兰花约 27%。
7. 数据来源：本地营养表和食物成分来源编号。
8. 免责声明：结果用于日常饮食记录，不替代医生或注册营养师的个体化建议。

页面上必须明确“份数只影响每份结果，不改变输入的总重量”。

#### P08 营养计算-部分未识别

在 P07 的基础上增加一条“羽衣甘蓝 100 克”，结果区显示黄色或橙色提示条：

> 有 1 项食材暂未匹配营养数据：羽衣甘蓝。该项未计入合计，请先补充营养或别名数据。

下方继续保留已识别食材明细和计算结果。未知食材不能被画成 0 kcal，也不能自动替换成相近食材。

如果所有食材都未识别，结果区只显示补数据提示，不展示伪造的总热量。

#### P09 反馈已记录

在 P03 的建议底部，点击“没帮助”后两个按钮都禁用，按钮下方显示“已记录，感谢反馈”。状态说明反馈不会改变本次推荐或下一次排序。

### 10.6 页面交互与连线

只实现以下关键交互：

1. 首页点击示例胶囊，自动填入对应自然语言输入。
2. 首页点击“生成建议”，进入 P02，等待约 1.5 秒后进入 P03、P04 或 P05。
3. 结果页点击“有帮助”或“没帮助”，进入 P09。
4. 顶部导航点击“营养计算”，进入 P06。
5. 营养页点击“+ 添加食材”，新增一行食材输入。
6. 营养页点击“删除”，移除当前食材行，至少保留一行。
7. 营养页点击“计算营养”，进入 P07；输入羽衣甘蓝时进入 P08。
8. 营养页输入空食材、0 克或不合法份数时，在对应字段下方显示错误提示，不提交请求。

连接线需要标注动作，例如“点击示例”“提交自然语言”“信息不足”“安全命中”“计算营养”“未识别食材”“记录反馈”。不要把每个组件都做成可点击热点。

### 10.7 原型文案规则

1. 使用真实、可读的中文，不使用 Lorem Ipsum 或“内容内容”占位。
2. 页面只出现用户能理解的语言，不出现接口名、Dify、API Key、CSV 字段名和代码错误。
3. 不写“已经通过用户验证”“用户很喜欢”“上线后提升 XX%”等未发生的结果。
4. 营养数字、份量和来源要一致，不能同一屏出现互相矛盾的数据。
5. 安全提示必须压过普通推荐，信息不足时必须先追问。

### 10.8 低保真视觉规则

1. 使用黑白灰线框为主，只保留一个绿色主色和一个橙色警示色。
2. 不使用真实照片、复杂插画、渐变、玻璃拟态、3D 图标和重度阴影。
3. 不使用移动端底部导航，不做响应式多端展开。
4. 输入框、按钮、卡片、标签、表格统一尺寸和圆角。
5. 文字层级最多四级：页面标题、区块标题、正文、辅助说明。
6. 优先保证信息层级、状态完整和可读性，不追求高保真装饰。

### 10.9 墨刀 AI 输出要求

1. 先输出页面地图，再输出画板，不要跳过页面结构直接画装饰。
2. 画板命名使用 `P01_首页_空状态` 这类格式。
3. 每个画板只表达一个主要状态，避免在一张画板上堆叠多个弹窗。
4. 完成后检查四个问题：缺信息会不会追问，风险请求会不会拦截，营养数字有没有来源，未识别食材会不会被静默算成 0。
5. 输出结果只是低保真原型，不代表产品已经完成真实用户验证或达到上线标准。
