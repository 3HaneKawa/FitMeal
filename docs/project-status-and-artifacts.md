## 1. 当前结论

FitMeal 已经具备可演示的完整产品链路，不是只有 PRD 或页面草图：

- 用户用一句话描述食材、目标、时间、地域和忌口。
- 系统完成意图识别、参数抽取、安全判断和候选筛选。
- 推荐、替换、营养解释和外食建议可以给出结构化结果。
- 营养计算、过敏过滤和推荐评分由 Python 与数据表完成，不依赖模型心算。
- 独立营养计算器支持输入食材、克重和份数，返回整份 / 每份营养、食材级拆解、来源和未识别项，不经过 Dify。
- 单输入前端通过 FastAPI 的 `/chat` 代理调用 Dify，浏览器不持有 API Key，也不回退到本地规则。
- 已建立 270 条正式评测集，代码层回归可以重复执行。
- 仓库只保留产品文档、代码、数据、评测集和演示截图，不包含内部脚本、原始回包和运行日志。

当前仍属于练习与验证项目。真实用户访谈本轮不安排；营养计算器已完成接口、页面和离线确定性回归，但没有真实用户验证；F10 只完成回答级最小反馈事件记录，对话反馈理解、偏好持久化和排序闭环未实现；真实 API 首轮结果仍是修复前基线，不能写成上线或优化后达标。

## 2. 解决的问题

目标用户是有明确健身目标、但没有固定饮食计划的人。常见任务不是“找一道菜”，而是在现有食材、时间、营养目标和外食环境下，快速决定这一顿吃什么。

v1 覆盖五条路径：

1. 自烹饪食谱推荐。
2. 外食和点餐策略。
3. 食材替换。
4. 营养查询与来源说明。
5. 安全风险拦截。

v1 不做账号、支付、外卖下单、医疗级建议和长期偏好学习。

## 5. 当前结果

### 代码层回归

当前离线版本为 `bv-a3e6abe13870`：

- 270 条中，234 条通过。
- 10 条失败。
- 14 条需要人工或 LLM 评分。
- 12 条为对话式反馈用例未就绪；最小反馈事件记录不在该 12 条内计数。

代码层结果用于确认规则、数据和本地筛选逻辑没有回归，不代表 Dify 完整链路已经通过。

### 真实 API 首轮

首轮请求经过 Dify Chatflow、LLM、FastAPI 和回答生成节点：

| 指标 | 结果 | 目标 |
| --- | ---: | ---: |
| 意图识别准确率 | 95.4% | ≥95% |
| 目标抽取准确率 | 91.3% | ≥90% |
| 地域归一化准确率 | 97.1% | ≥90% |
| 时间抽取准确率 | 97.9% | ≥90% |
| JSON 解析通过率 | 100% | 100% |
| 安全 LLM 判定准确率 | 88.9% | ≥95% |
| 食材抽取准确率 | 52.5% | ≥90% |
| P95 响应时间 | 26.08s | ≤8s |

这轮结果是修复前基线。首要问题不是继续扩功能，而是修复安全分类、信息追问、过敏判定口径和食材治理。

### 独立营养计算器离线回归验证

本轮对计算接口、页面和确定性回归脚本做了验证，覆盖正常计算、别名、份数、未识别食材和非法输入：

- 鸡胸肉 150 克 + 西兰花 200 克，按 2 份计算：整份 248 kcal，每份 124 kcal；蛋白质、脂肪、碳水和膳食纤维也分别返回整份与每份结果。
- “西红柿”可按别名归一为“番茄”，100 克返回 18 kcal。
- 未识别食材进入 `unresolved`，不按 0 静默混入合计；已识别食材仍继续计算。
- 克重为 0、负数、非数字，以及份数为 0、非整数或超过 100 时均返回输入错误。

这些只能证明确定性计算、错误处理和基本页面状态可用，不能证明真实用户已经理解或认可该工具。

## 6. 已知限制

1. 真实用户访谈未完成，当前用户画像来自公开产品观察、场景拆解和自用流程。
2. 没有留存采纳率、决策率、付费意愿等真实行为指标。
3. 安全 LLM 判定和食材抽取没有达到 PRD 目标。
4. 过敏自动口径受到字符串误判影响，当前 14.3% 不能直接解释为漏放过敏原的比例。
5. 缺少食材或目标时，系统仍可能直接推荐，需要增加强制澄清门禁。
6. P95 延迟为 26.08 秒，主要来自串行模型节点和同步数据检索。
7. F10 只完成最小反馈事件记录；反馈不会自动改变推荐，12 条对话式反馈用例仍为 `not_ready`。
8. 当前反馈入口是回答级“有帮助 / 没帮助”，暂不能区分推荐、外食、替换、营养和安全分支，也没有反馈闭环。
9. 当前不能宣称产品达到上线标准。
10. 营养计算器当前只接收克重，不处理“个 / 瓣 / 碗”等非重量单位，也尚未做真实用户可用性测试。
