## 2. 已经验证的事实

1. 规则层可以稳定读取并校验现有数据表。
2. 本地前端已经通过结构化请求调用 FastAPI，而不是静态页面占位。
3. 食谱、外食、替换、营养、安全五条路径都有实际响应。
4. 270 条评测集的结构、枚举、能力引用和 dev/holdout 划分通过校验。
5. Dify API 第一轮完整跑完，保留了原始分流和逐用例结果。
6. 首轮结果中，理解和 JSON 格式化已经接近可用水平，但安全、过敏和澄清没有达到上线门槛。

## 3. 下一轮开发顺序

### P0.1 安全判据与风险分类

目标：

1. 把 S1 至 S5 的判定条件写成可执行规则，避免同一请求在不同模型节点中得到不同风险类型。
2. 区分“推荐了过敏原”和“安全提示中提到了过敏原”。
3. 对 P037、P044、P046、P213、P215、P236 等高风险用例建立回归样本。
4. 先跑高风险切片，再跑完整 270 条。

完成标准：

- S2-S5 高风险请求全部进入安全分支。
- 风险类型与 PRD 定义一致，不能只满足“有拦截”。
- 过敏原泄露的人工复核记录可以追溯到具体回答和判定理由。

### P0.2 信息缺失时先追问

目标：

1. 缺少食材时先问用户现有食材、可接受替代或直接放宽到通用推荐。
2. 缺少目标时先问减脂、增肌还是维持。
3. 目标冲突时要求用户选择主目标，并说明不同选择的结果差异。
4. 约束互相冲突时，明确说明无法全部满足，给出降级方案。

完成标准：

- P047、P250、P249 等澄清用例不再直接给出无依据推荐。
- `clarification_required`、`explains_conflict`、`explains_tradeoff` 可以通过真实 API 复跑。
- 追问不会阻挡正常的完整输入。

### P1.1 食材抽取与数据治理

处理顺序：

1. 先统计失败属于用户表达、别名、单位、复合食材、否定表达还是候选数据缺失。
2. 能通过别名和单位解决的，更新词表；能通过数据补充解决的，补食谱或营养表。
3. 只有确认属于模型理解问题，才调整提示词或模型参数。
4. 每类失败保留至少一个回归用例。

完成标准：

- 食材抽取的失败原因可以拆分统计。
- 新增数据不改变已有用例的期望口径。
- 食材命中率、候选缺失率和安全过滤结果分别记录。

### P1.2 替换和外食边界

1. 替换建议必须说明替换关系、适用条件和营养变化。
2. 外食建议不能编造品牌营养数据，无法确认的品牌只给点餐原则。
3. 没有合适候选时，说明限制并给出放宽项。
4. 补充人工 rubric，处理机检无法判断的解释质量。

### P2 性能与体验

安全、澄清和数据问题稳定后再做：

1. 合并可以并行的模型节点。
2. 减少重复调用和同步数据检索。
3. 评估检索缓存和结果缓存。
4. 目标是 P95 低于 8 秒，但延迟优化不能改变推荐和安全结果。

### P1.3 用户研究与反馈闭环

1. 后续单独招募 5 至 10 位目标用户，覆盖减脂、增肌、维持和外食场景。
2. 记录用户是否在三次推荐内做出选择，以及没有选择的原因。
3. 当前已有采纳、不喜欢、太麻烦和换一批事件记录；只有在真实交互和用户测试完成后再考虑偏好持久化、候选排除和排序调整。
4. 研究结论需要回写 PRD，不只在作品集里口头描述。

## 5. 风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 过敏字符串断言误判 | 可能把安全提示当成过敏原推荐 | 增加人工复核和上下文判定，不直接放宽过滤 |
| 风险类型不一致 | 用户看到安全提示，但问题分流错误 | 固定 S1-S5 判据，单列高风险回归 |
| 食材密度不足 | 冷门食材组合没有候选 | 保留无匹配说明，优先补目标食材和常见组合 |
| 营养来源不统一 | 推荐解释与数据来源不一致 | 保留来源等级、数据版本和校验脚本 |
| 模型节点串行 | 延迟过高，影响体验 | 安全与澄清稳定后并行化 |
| 无真实用户数据 | 无法证明采纳率 | 明确标注待验证，不用模拟数据替代 |
| 内部配置泄露 | 公开仓库出现密钥、工作流 ID 或原始回包 | `.gitignore` 排除运行记录和原始数据，提交前扫描 |

## 6. 每次迭代的完成标准

1. 需求变化先更新 PRD，再修改实现和用例。
2. 修复代码后先跑相关高风险切片，再生产完整运行记录。
3. 失败要归到一个明确原因：实现、数据、PRD 或用例。
4. holdout 只在验收时运行，不用于调参。
5. 公开仓库只提交可复现代码、核心数据和结论文档，不提交原始请求、密钥和内部日志。
